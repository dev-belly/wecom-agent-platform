# 索引重建：失败时继续查询同一个完整版本

## 发现的业务错误

旧代码先原地替换 BM25，再构建向量，最后替换结构化表格。假设旧文档包含客户 C1 的 10 元持仓，新文档包含 C2 的 20 元持仓：如果向量编码或写入失败，检索会读到 C2，确定性持仓查询却仍读到 C1，服务还标记为已初始化。

另一个错误来自复用同一个 Chroma collection，并始终用 `doc_0`、`doc_1` 等编号 upsert。把三条记录重建为一条时，仅替换 `doc_0`，旧 `doc_1/doc_2` 仍可能被向量召回；它们已经不在本次文档集合中。

这两个问题都与模型回答能力无关，而是数据版本的业务一致性问题。

## 现在的规则

`build_index_from_parsed` 在独立状态中准备 BM25、向量集合、重排器和完整结构化表格；全部成功后，在锁内一次发布新状态引用。它返回本次发布的 `index_revision`。任何准备阶段失败，都不改动当前可查询状态；首次构建失败时继续保持未就绪。

每次 `retrieve` 和每次合同/持仓工具查询都捕获一个状态引用，直到本次查询结束。即使重建在 BM25 召回后完成，本次后续向量召回和重排仍使用捕获的旧版本。持仓遍历期间发布新版本，也不会把前半段旧记录与后半段新记录加在一起。

写者由进程内构建锁串行化，读者不等待完整重建。构建 API 改为同步路由，由服务的工作线程执行，避免解析和索引构建占住异步请求线程。新的向量集合有独立的随机版本名，不写入正在被读取的旧集合。

## 向量集合生命周期

| 状态 | 处理 |
|---|---|
| 构建过程中失败 | 清理本次新建的集合，继续使用旧版本 |
| 成功发布，旧版本没有读者 | 立即删除旧版本集合 |
| 成功发布，仍有旧版本读者 | 最后一个旧版本读者结束后再删除 |
| 正常关闭服务 | 停止接受新快照；已有读者结束后清理其集合 |
| 删除暂时失败 | 记录 `cleanup_pending` 并输出服务日志；下一次重建及关闭时重试 |

清理只针对本进程创建并登记的具体版本名。不枚举并删除同前缀集合，不碰旧的共享 collection 或其他应用的数据。正常重复重建且清理可用时只保留一个当前版本；在途旧查询、清理失败会暂时保留额外版本。

这里使用 Chroma 的独立 collection 创建与定向删除接口；参见[官方客户端接口说明](https://docs.trychroma.com/reference/python)。不调用清空数据库的 `reset`。

## 接口如何区分结果

`POST /api/index/build` 沿用 API Key 鉴权。

- 成功重建：200，`status="ok"`、`index_rebuilt=true`，返回本次发布的 `index_revision`。
- 已初始化且 `force_rebuild=false`：200，`status="unchanged"`、`index_rebuilt=false`。解析完成不代表新文档进入了当前索引。
- 解析内容无法建索引：422，说明未改动原索引。
- 模型或向量构建失败：503，`detail` 包含中文错误说明、`index_preserved` 和保留的 `index_revision`，不会给“重建成功”。错误响应不暴露底层服务异常详情。

`GET /api/index/status` 捕获一个完整状态，返回当前版本、BM25 文本数、结构化行数、向量条目数和 `cleanup_pending`。该版本号是当前服务状态；不同 HTTP 请求可能发生在不同版本上，不把多个独立请求称为同一个事务。

合同与持仓查询响应也直接返回 `index_revision`，包括没有匹配记录的结果。它来自计算本次结果时捕获的同一个版本；调用方不需要再查当前 status 为旧查询补上可能已经更新的版本号。

## 复现与验证

```bash
uv sync --locked --extra dev
uv run --locked pytest tests/test_index_snapshots.py -q
```

默认环境使用轻量向量协议替身，直接运行实际索引、业务工具、版本发布与清理代码。失败注入覆盖编码失败、部分 upsert 后失败和重排器失败。确定性交错测试把查询暂停在 BM25 后再重建，验证随后仍读旧集合，且读完才删除；另一个测试在持仓遍历第一行时重建，验证旧版本仍汇总为 21.00，而下一次查询读到新版本 100.00。

还有缩小语料、重复重建资源数、初次失败 readiness、关闭时在途读者、清理失败重试，以及鉴权 API 失败响应/显式跳过。可选 Chroma 安装时，额外运行实际持久化存储的版本/清理回归；该测试使用固定向量生成器，不加载模型或声称验证了语义召回质量。

Linux CI 另外安装 `uv.lock` 当前固定的 `chromadb==1.5.9`，用虚拟环境 Python 直接运行 `-k actual_chroma` 存储回归，确保它不会因默认未安装可选依赖而被跳过。这一步不安装其余检索模型依赖。

## 保留的边界

这是一项**单进程内存索引**的发布与读者生命周期约束，不是数据库事务或跨实例一致性协议。构建期间可能同时持有新旧索引与模型，必须为额外内存留出空间；长时间不结束的旧查询也会延迟清理。

解析器会写入中间 JSON，本次修改没有让这些磁盘文件与内存状态组成持久化事务。进程崩溃可能留下未清理的向量集合，也不会保存内存里的待清理队列；重启时仍从解析文件重建。运行人员需要检查这些残留，程序不会为清理它们猜测并删除共享存储的数据。

重复上传相同业务头寸、持仓快照日期、租户权限和业务主键去重仍需另行定义；此次只修复一次索引更新把数据版本混在一起的问题。

面试可直接讲清：“我在更新文档时注入向量写入失败，发现文本检索与金额汇总来自不同版本。修复采用完整准备后一次发布，每个查询固定引用一个版本，再用读者计数决定何时清理向量集合。测试同时验证失败保留旧版本、查询中途更新仍不混读，以及重复重建不无限残留。”这些行为可现场复现，不需要编造生产流量或故障经历。
