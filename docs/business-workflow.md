# 合同筛选与持仓汇总：能复现的业务链路

这部分解决的是运营查询的正确性：查一个合同不能混入相似编号，查客户持仓不能漏掉第 11 条，更不能把缺失估值算成零。本仓库没有真实客户、交易量或生产运行记录；下面的样例都是虚构业务数据。

## 一分钟复现

```bash
uv sync --locked --extra dev
uv run --locked python scripts/business_query_demo.py
uv run --locked pytest tests/test_business_queries.py -q
```

样例来源是 [`data/business-demo/parsed.json`](../data/business-demo/parsed.json)，它是与 PDF 解析器输出同形状的虚构 JSON，并非随附的真实 PDF。脚本将它读入实际索引，再调用实际业务工具，输出四个带来源的场景：

| 场景 | 期望结果 |
|---|---|
| 查询 `HT001` | 仅一个合同；`HT0010` 不会混入 |
| 2024 年签约、金额至少 1000.10 CNY | 日期及金额同时满足；美元合同不参与人民币比较 |
| 查询 `C10086` 全部持仓 | `1000.30 CNY`；张三丰的记录不混入 |
| 查询 `C20000`，其中一笔待估值 | 已计价小计 `25.00 CNY`；完整总额为 `null`，附缺失原因 |

脚本明确关闭可选向量模型，安装 retrieval 扩展的环境也不会下载模型。服务仍可将自然语言交给 Agent；这两个 REST 查询入口不依赖 LLM。

## 业务规则与返回契约

`POST /api/contracts/query` 接受 `contract_id`、`party_a`、`party_b`、`date_range_start`、`date_range_end`、`min_amount`、`currency`。

- 合同编号是精确匹配；甲乙方名称使用明确的包含匹配；多条件同时满足。
- 签约日期包括起止两天。启用日期筛选时，缺失或无效日期的记录不能证明符合条件，会被排除。
- `min_amount` 是指定币种的基本单位金额，必须同时给出 `currency`；不会换算汇率。缺失币种、含糊金额和单位冲突不能满足金额筛选。
- 金额支持明确数字、合法千分位、`元/万元/亿元` 或 `万/亿` 倍数。含“元”的中文单位明确表示 CNY；裸数字不推断币种。`约 100 万`、百分比、科学计数文本及歧义货币符号被拒绝。
- 起始日晚于截止日、空白条件、未支持的筛选字段直接返回 422，不悄悄忽略。
- `count` 覆盖全部匹配记录；列表最多返回 10 条，`returned_count` 和 `truncated` 标明展示边界。

`POST /api/holdings/query` 接受 `customer_id`、`customer_name`、`product_code`，都使用精确匹配，多条件同时满足。

- 数字形式的客户/产品编号在 PDF 导入时保留原始文本，`001234` 不会变成 `1234`。
- 所有匹配表格行都参与汇总，列表最多展示 20 条。正文段落仅用于检索发现，不作为可汇总的业务记录。
- `total_value_by_currency` 逐币种输出精确十进制字符串。计算使用 Decimal，JSON 不转浮点。源数字最多支持 38 位，计算精度为 64 位，单位换算后不主动舍入。
- `total_value` / `total_currency` 只在全部记录可计价且币种唯一时提供。多币种保留各币种总额，不生成不存在的统一金额。
- 无效金额、缺失币种或冲突声明会产生 `amount_error`、`unpriced_count`、`warnings`；`totals_complete=false`，总体金额为 `null`。可计价记录仍提供小计。
- 没有匹配记录与真实零估值不同：前者 `count=0`、总额为 `null`；后者可以明确返回 `"0.00"`。

每条记录的 `metadata` 包含 `source`、`page`、`page_end`、`table_index`、`row_index`。页码从 1 开始，表格/行索引从 0 开始。可以据此回到原文件核对。查询范围是全部**已索引**表格，不代表所有客户文件或所有外部系统数据。

两个入口沿用现有 API Key 鉴权；生产环境要求至少 32 字符密钥。索引未就绪返回 503。部署设置密钥后，请在下列请求中加入 `Authorization: Bearer <API_KEY>`。

```bash
curl -X POST http://localhost:9000/api/contracts/query \
  -H "Content-Type: application/json" \
  -d '{"contract_id":"HT001"}'

curl -X POST http://localhost:9000/api/holdings/query \
  -H "Content-Type: application/json" \
  -d '{"customer_id":"C10086","product_code":"001234"}'
```

离线样例脚本不会修改生产索引；REST 示例需要先将实际文档放入配置目录并构建索引。

## 为什么这样设计

`PDF → 原始结构化行与来源 → 全表条件筛选/精确汇总 → 结构化 API` 是权威查询链路。`自然语言 → 意图及参数 → 同一业务工具 → LLM 格式化` 是交互链路，两者共用业务实现。

BM25/向量检索回答“哪些文本可能有关”。金额阈值、精确身份和总持仓回答“哪些记录满足条件、所有满足条件的金额是多少”。后者不能在 top-k 候选集上定义；即使相关度排序很好，也无法证明第 11 条不存在。因此合同和持仓工具扫描索引保留的完整表格记录，其他发现类工具继续使用检索。

金额不能在导入阶段转 float：不仅 `0.1 + 0.2` 的二进制表示有误差，大金额也可能丢掉整数位。解析器对金额字段保留原文本及单位，业务层验证后转 Decimal。旧解析文件中已经丢掉的前导零或精度不能靠本次修改恢复；应从原始 PDF 重新解析。

未定价头寸是一种数据状态。返回零会误导运营；丢掉该行再报“总额”也不对。所以保留原记录和错误，输出明确的小计与完整性标记。字段别名冲突会拒绝查询，要求修复数据，不能省略有问题的记录后仍声称完整。

当前是单进程内存索引的线性扫描，适合本地评审和有限文档集；索引层已有[查询快照与重建失败隔离](index-snapshots.md)，但没有数据库索引、租户级授权、持仓业务主键去重、业务快照日期或生产服务等级承诺。两个文件若重复导入同一个头寸，目前会作为两条原始记录参与计算；部署前必须确定持仓业务主键及快照日期，再将去重/版本约束放进持久化层。不能仅因这部分正确就宣称已经投产。

## 面试时可讲的一条主线

**开场 60 秒：**

“我做的是金融运营文档查询原型，其中重点补了一条可核对的业务路径。最早的实现把合同条件当检索词，再取前 10 条，持仓金额又在文本序列化后失去类型，汇总会返回零。我把检索发现和权威条件查询拆开：导入时保留完整表格行、编号原文和页码；合同/持仓使用确定性筛选，金额用 Decimal 分币种汇总。比如客户有 25 条头寸，界面只展示 20 条，但汇总必须覆盖全部 25 条；某条待估值时只能显示小计，不能给完整总额。这个规则在实际索引、工具、HTTP 鉴权和 Agent 降级路径上都有离线回归，可以现场复现。”

| 追问 | 可以展开的回答及证据 |
|---|---|
| 为什么不直接增强 RAG？ | 相似度不能证明完整性；`test_holding_sum_covers_all_rows_before_display_truncation` 用 25 条验证全量汇总 |
| 为什么 JSON 金额是字符串？ | 保留十进制精度，调用方需要显式转 Decimal；`test_holding_money_never_rounds_through_float` 验证超过 JavaScript 安全整数范围的金额 |
| 用户输金额没给币种呢？ | 参数模型拒绝，Agent 追问；不猜人民币，也不拿美元直接比；`test_agent_asks_for_currency_before_executing_an_amount_query` |
| LLM 挂了还能做业务吗？ | 两个确定性 REST 查询不依赖模型；Agent 格式化失败仍展示精确汇总与来源 |
| 如何查错数据？ | 每行包含文件、跨页范围、表格/行位置；无效金额保留原行并给错误原因 |
| 现在离生产还有什么？ | 持久化恢复、租户/字段权限、持仓快照主键及幂等导入、跨进程索引一致性、真实数据评估；本仓库没有生产流量可证明这些 |

讲这些时应能亲自解释查询条件、币种和完整性规则，现场修改一个样例再跑测试。代码和可复现结果可以证明实现；它们不能替代对设计的理解，也不能证明尚未发生的上线经历。
